# llm-quant-bench

[English](README.md) · [中文](README.zh-CN.md)

![ci](https://github.com/jiadewoer/llm-quant-bench/actions/workflows/ci.yml/badge.svg)

**一块 8GB 消费级显卡到底能跑多大的模型？**

在一台 RTX 4060 Laptop（8188 MiB）上，用 Ollama 实测「模型尺寸 × 量化等级 ×
上下文长度」三条轴。每个数字都在这台机器上实测，也都事先预测过——**两者之间
的差距才是这个项目的重点。**

---

## 四条结论

**1 · 卸载的代价比「模型大一倍」还大。**
Qwen2.5-14B 在 q4_K_M、同样上下文下比 7B 慢 **6.28 倍**（8.27 对 51.94
tok/s）。这个倍数可以干净地拆开：**1.94 倍**来自模型本身大一倍，**3.23 倍**
来自 39.7% 的部分被推到系统内存。在一块装不下它的卡上，卸载的惩罚超过尺寸的
惩罚。

**2 · 上下文悬崖高度非线性。**
从 ctx 8192 到 16384，只有 **6.8%** 的字节掉出显存，吞吐却损失了
**33.5%**——放大 4.9 倍。「93% 还在 GPU 上」听起来像四舍五入，实际是 1.5 倍
的减速。而在拐点以下，上下文是免费的：2K 到 12K 全部跑在 51.8 ± 0.2 tok/s。

**3 · `OLLAMA_NUM_PARALLEL` 是一个隐藏的 4 倍乘数。**
不显式设置时，Ollama 会根据可用显存自己在 1 和 4 之间挑。由于 `num_ctx` 和
`num_parallel` 在 KV Cache 公式里是同一个乘积项，实测 ctx 8192 × 4 槽位与
ctx 32768 × 1 槽位**占用的显存精确到字节完全相同**，两组独立配对都吻合。
同一份配置在不同时刻可能悄悄需要 4 倍显存。

**4 · 量化到 q4_K_M 没有可测量的代价。**
q8_0 得 81/100，q4_K_M 得 80。逐题配对后两者**在 100 题中的 97 题判定相同**，
三对不一致按 1:2 分裂，McNemar 精确检验 **p = 1.000**。两者共同答错的是同一
批 18 题，说明 q4 没有引入任何新的失败模式。而它省下 3.33 GiB——约 27000
tokens 的上下文——并且保持完整驻留，而 q8 在 ctx 4096 下就已经卸载了 34%。

![卸载悬崖](docs/images/cliff.png)

## 显存模型

三项，只有第一项是教科书上有的。

```
SIZE ≈ 权重 + KV Cache + 额外项
```

**权重。** 每参数字节数是实证标定的，基准是 `ollama list`。q4_K_M 实测
0.614 字节/参数，不是名义上的 0.5——GGUF 会把 embedding 和部分注意力张量保留
在更高精度。

**KV Cache。** 唯一的教科书项：

```
KV_bytes = 2 × 层数 × KV头数 × head_dim × num_ctx × num_parallel × 每元素字节
```

开头的 2 是 K 和 V 各存一份。**GQA 是这一切能装下的前提**：Qwen2.5-7B 有 28
个注意力头但只有 4 个 KV 头，省了 7 倍。没有它，32K 上下文光缓存就要约
12 GiB。

**额外项——机理未知。** 7B 实测每 token 的上下文成本是 **128.0 KiB**，而理论
KV 只有 56.0。详见下面的[我们错在哪](#我们错在哪)——诚实的答案是我们缩小了
范围，但没有解决它。

### 精度

在 11 个配置上（跨三种模型尺寸、两种量化、六种上下文长度）：**SIZE 平均绝对
误差 0.159 GiB，GPU 驻留比例平均绝对误差 0.6 个百分点。** 其中五个配置从未
参与标定，误差全部小于 0.26 GiB。

![估算器精度](docs/images/prediction.png)

最尖锐的一次检验：`ctx 12288` 这一行纯粹是为了夹住拐点而加的。估算器算出它
距离预算只差 0.01 GiB——实测它确实保持 100% 驻留，而 16384 掉了下去。

完整表格见 [`results/summary.md`](results/summary.md)。

## 我们错在哪

三个系统性错误，外加一个被推翻的假设。**这一节存在的理由是：修正过程比最终
数字更有信息量。**

### 1 · 显存预算是拍脑袋定的

初版假设 Ollama 能用显卡容量的 92%，即 7.36 GiB 预算。而实测所有卸载配置的
精确 `size_vram` 都聚集在 **5.63–5.87 GiB**，Ollama 在桌面 baseline 之外还
留了约 1.1 GiB 不碰。那个假设高估了 30%，也正是初版预测「ctx 16384 能完整
驻留」而实际不能的原因。

### 2 · 单位搞错了

`ollama ps` 和 `ollama list` 报的是**十进制 GB**（字节 ÷ 10⁹），不是 GiB。
拿 GiB 预测值去和那一列比较，会带来 7.4% 的静默偏差，而这个错误持续了三天。
改读 `/api/ps` 的精确字节数之后才暴露出来。重新拟合得到的上下文斜率是
**恰好 128.0 KiB/有效 token**，截距 4.084 GiB——P=4 那个点精确落在这条直线上，
吻合到小数点后三位。

### 3 · 漏了一整项显存开销

实测的上下文成本是理论 KV 的 2.286 倍。初版只有 KV 一项，对 ctx 32768 低估了
1.5 GiB。

### 4 · 那一项的解释被推翻了两次

**第一个假设**：多出来的是 llama.cpp 显式物化的注意力分数缓冲区，只在关闭
flash attention 时存在。这个假设可以证伪，于是就去测了：把
`OLLAMA_FLASH_ATTENTION` 从 0 改成 1，其余条件全部不变，重测 ctx 16384。
**SIZE 纹丝不动**——两种设置下都是 6.5 GB、12%/88% 的切分。最可能的原因是
Ollama 0.24 已经完全忽略这个变量。

**第二个假设**：多出来的是 KV Cache 的固定倍数。14B 的上下文扫描能区分它，
因为 14B 的 H/H_kv 比例与 7B 不同。这个假设预测 14B 是 247 KiB/token，
**实测 92**。推翻。它之所以在 7B 上看起来完美，只因为它就是在 7B 上标定的。

**存活下来的部分**：这一项随注意力头数 H 增长，而非 KV 头数 H_kv——实测的
14B/7B 比值是 1.28，该形式预测 1.43，KV 倍数形式预测 3.43。但数值上偏低
约 15%。

**两个假设都没预料到的事**：额外项在小上下文下**精确为零**。14B 从 ctx 4096
到 8192 的边际成本是 192.0 KiB/token，而理论 KV 正好是 192.0。所以这多出来的
开销根本不是一个每 token 缓冲区——**它有阈值**。下一个该做的实验是 `num_batch`
扫描，因为 `n_batch` 只出现在存活的那个候选里。

估算器保留了这一项，命名为 `extra_context_gb`，并在文档字符串里明确写着机理
未知。

### 全部修正之后

| | 初版 | 第三版 |
|---|---|---|
| SIZE 平均误差 | 约 1.5 GiB | **0.159 GiB** |
| GPU 驻留比例平均误差 | — | **0.6 个百分点** |

## 精度评测

100 道人工核对过的题目，覆盖算术、常识、推理、代码、中文五类，判分完全确定
性——**不用 LLM 当裁判**，因为裁判跑在同一块 8GB 卡上，会把自己的误差混进来。

| 模型 | 量化 | 算术 | 中文 | 代码 | 常识 | 推理 | 总分 |
|---|---|---|---|---|---|---|---|
| Qwen2.5-7B | q8_0 | 17/20 | 18/20 | 13/20 | 18/20 | 15/20 | **81** |
| Qwen2.5-7B | q4_K_M | 17/20 | 18/20 | 12/20 | 18/20 | 15/20 | **80** |
| Qwen2.5-14B | q4_K_M | 18/20 | 18/20 | 15/20 | 18/20 | 16/20 | **85** |

**评测集本身修正了两次，分数才变得有意义。** 生成的初稿把正确答案放在 B 的
比例高达 62%——一个永远答 B 的模型能拿 58 分。而第一次基线跑出来的错题里，
有一批是短答案题要求数字、模型给出了带单位的正确数字却被判错。**改题目而不是
放宽判分器**，基线从 77 提到 81。详见
[`results/day5_eval_zh.md`](results/day5_eval_zh.md)。

14B 多出来的 5 分全部来自代码、算术和推理，常识与语言类一分未涨，代价是慢
6.28 倍。

## 快速开始

```bash
git clone https://github.com/jiadewoer/llm-quant-bench.git
cd llm-quant-bench
uv venv
.venv/Scripts/activate.bat      # Windows；其他平台用 source .venv/bin/activate
uv pip install -e ".[dev]"

python scripts/check_env.py
pytest -v
lqb estimate --model qwen2.5-7b --ctx 16384
```

Windows 上双击 `dev.bat` 可以一步搞定切 UTF-8 代码页和激活虚拟环境。

### 先钉死 Ollama 的运行时变量

**这几个变量不固定，结果就不可复现。** 设完之后从托盘退出 Ollama、重新启动，
再开一个新终端——已经在跑的终端和 Ollama 服务都不会重新读环境变量。

```
setx OLLAMA_NUM_PARALLEL 1
setx OLLAMA_KEEP_ALIVE 30m
setx OLLAMA_FLASH_ATTENTION 0
setx OLLAMA_KV_CACHE_TYPE f16
```

`check_env.py` 会逐一验证。

### 命令

```bash
lqb estimate --model qwen2.5-14b --ctx 4096   # 预测显存需求
lqb ps                                        # 当前加载了什么，精确字节数
lqb bench --model qwen2.5:7b --ctx 8192       # 吞吐与首 token 延迟
lqb matrix                                    # 跑整个矩阵
lqb eval --model qwen2.5:7b                   # 精度评测
lqb review results/eval_<label>.json          # 逐条查看错题与模型原始回复
lqb report                                    # 出图与对比表
```

## 已知限制

- **卸载配置的吞吐重复性只有 ±10%。** 完整驻留的配置重复性在 ±0.3% 以内，
  卸载的配置在两次会话之间差了 7–11%，因为层的切分是在加载那一刻根据可用显存
  动态决定的。本文所有卸载配置的数字都是单次测量，请按这个区间理解。
- **`gpu_ratio` 是字节比例，不是层数比例。** SIZE 里包含 KV Cache 和那个未知
  项，它们都不是「层」。「卸载 6.8%」只是卸载程度的代理指标。
- **单机单卡。** 所有结论不经重新测量不能推广到桌面版 4060 Ti 16GB 或 Apple
  统一内存。
- **P=4 ctx32768 那一行不支持任何定量结论。** 它报告 9.014 GiB 驻留在一块
  7.996 GiB 的卡上——Windows 驱动把系统内存伪装成了显存。它只作为「显存超配」
  的定性证据，已从所有统计中排除。
- **100 道题**给出的非配对区间是 ±7.7 个百分点。配对设计能走得更远，但要在
  p < 0.05 下检出任何精度差异需要约 8 对不一致，而 q8 与 q4 之间只有 3 对。
- **权重估算对 2B 以下的模型偏低**，因为词表 embedding 占比过大。3B 那行偏差
  0.19 GiB 就是这个原因。
- **`extra_context_gb` 没有确立的机理。**
