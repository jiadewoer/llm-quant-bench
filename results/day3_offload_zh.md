# Day 3 · 卸载行为实测

**日期** 2026-08-29
**硬件** RTX 4060 Laptop，8188 MiB，驱动 580.88，32 GB 内存
**运行时** Ollama 0.24.0，Windows 11 (26100)
**已固定的变量** `OLLAMA_NUM_PARALLEL=1`、`OLLAMA_KEEP_ALIVE=30m`、
`OLLAMA_FLASH_ATTENTION=0`、`OLLAMA_KV_CACHE_TYPE=f16`

未加载任何模型时的桌面显存占用（baseline）：五次读数在 **1.13 – 1.75 GiB**
之间。下面所有测量都是在这个范围内做的。

---

## 1. 尺寸与量化轴

用 `ollama run <模型> "hi"` 测的，所以四行都用的是 Ollama 的默认上下文
**4096**，不是 2048。

| 模型 | 量化 | SIZE | PROCESSOR | 预测值 | 误差 |
|---|---|---|---|---|---|
| qwen2.5:3b | q4_K_M | 2.4 GB | 100% GPU | 2.16 | −0.24 |
| qwen2.5:7b | q4_K_M | 4.9 GB | 100% GPU | 5.12 | +0.22 |
| qwen2.5:7b-instruct-q8_0 | q8_0 | 8.5 GB | 34%/66% CPU/GPU | 8.53 | +0.03 |
| qwen2.5:14b | q4_K_M | 10 GB | 47%/53% CPU/GPU | 10.14 | +0.14 |

**PROCESSOR 这一列是核心证据。** 7B 在 q4 下全部驻留 GPU，换成 q8 就有
34% 掉到 CPU 上；14B 在同样的 q4 下也掉了 47%。这两处就是「量化悬崖」和
「尺寸悬崖」。

3B 那行预测偏低，原因估算器注释里写了：它的词表 embedding 占了整个模型的
27%，而 embedding 不按 q4 存。

---

## 2. 上下文轴（qwen2.5:7b q4_K_M，P=1）

| num_ctx | SIZE | PROCESSOR | 预测值 | 误差 |
|---|---|---|---|---|
| 2048 | 4.8 GB | 100% GPU | 4.90 | +0.10 |
| 8192 | 5.3 GB | 100% GPU | 5.56 | +0.26 |
| **16384** | **6.5 GB** | **15%/85% CPU/GPU** | 6.43 | −0.07 |
| 32768 | 8.7 GB | 36%/64% CPU/GPU | 8.18 | −0.52 |

**拐点在 8192 和 16384 之间。**

实测之前的估算器预测这四行全都能完整装进显存。它错了，原因见第 5 节。

## 3. 并发槽位轴（qwen2.5:7b q4_K_M，P=4）

| num_ctx | SIZE | PROCESSOR | 等价的 P=1 配置 | 那个配置的 SIZE |
|---|---|---|---|---|
| 2048 | 5.3 GB | 100% GPU | ctx 8192 | **5.3 GB** |
| 8192 | 8.7 GB | 31%/69% CPU/GPU | ctx 32768 | **8.7 GB** |
| 16384 | 12 GB | 54%/46% CPU/GPU | ctx 65536 | 未测 |
| 32768 | 21 GB | 55%/45% CPU/GPU | ctx 131072 | 未测 |

### 交叉验证精确成立

估算器把 `num_ctx` 和 `num_parallel` 当成同一个乘积项，由此推出一个预言：
**ctx 8192 配 4 个槽位，和 ctx 32768 配 1 个槽位，占用的显存必须完全相同。**

实测了两组独立的配对，两组都精确相符，连显示的小数位都一样。

这是今天最强的结果。它意味着 `OLLAMA_NUM_PARALLEL` 这个变量——在不显式设置
时 Ollama 会自己在 1 和 4 之间挑——会**悄悄把显存占用乘上最多 4 倍**，足以
让一个原本完整驻留的配置变成一半卸载到 CPU，而使用者完全看不到原因。

### 那个"不可能"的数据点：不是显示错误

ctx 32768 × P=4 那行显示 21 GB、45% 在 GPU 上，相乘约 9.5 GiB。但这块卡只有
7.996 GiB。

用 `/api/ps` 取精确字节数复核：

```
size      = 21,565,124,608 B = 20.084 GiB
size_vram =  9,678,372,864 B =  9.014 GiB
ratio     = 44.9%   （与显示的 45% 一致）
```

**排除了四舍五入。Ollama 报告有 9.01 GiB 驻留在显存里，比物理容量多出
1.02 GiB；扣掉 1.34 GiB 的桌面 baseline，超出可用显存 2.36 GiB。**

#### 解释：Windows 的 System Memory Fallback

NVIDIA 驱动在 Windows 上默认开启显存回退（536.xx 之后，本机驱动 580.88）。
显存不足时驱动不会返回 OOM，而是把系统内存映射成 GPU 可访问的地址空间，
通过 PCIe 访问。

从 CUDA 的角度这次分配是"成功"的，所以 Ollama 如实报告了 9.01 GiB。但其中
约 2.4 GiB 实际位于 DDR5 内存条上，访问带宽比真显存低两个数量级。

**这是一个完全静默的性能悬崖。** 使用者看到 `45% GPU` 会以为一半的计算在
显卡上，实际那 45% 里还有一半是伪装成显存的系统内存。全程没有任何报错或
警告。

#### 待验证

Day 4 测吞吐时，这个配置的 tokens/sec 应该显著低于 45% 这个数字所暗示的
水平。如果它比 `7b-q4-ctx16384`（88% GPU）慢的倍数远超两倍，则解释成立。

## 4. Ollama 实际会用多少显存？

从每个发生卸载的配置反推：`SIZE × GPU%` 就是实际驻留在显存里的字节数。

| 配置 | SIZE | GPU% | 实际驻留 |
|---|---|---|---|
| 7b-q8 ctx 4096 | 8.5 | 66% | 5.61 GB |
| 14b-q4 ctx 4096 | 10.0 | 53% | 5.30 GB |
| 7b-q4 ctx 16384 | 6.5 | 85% | 5.52 GB |
| 7b-q4 ctx 32768 | 8.7 | 64% | 5.57 GB |
| 7b-q4 ctx 8192 P4 | 8.7 | 69% | 6.00 GB |
| 7b-q4 ctx 16384 P4 | 12.0 | 46% | 5.52 GB |

六个完全不同的配置，落在 5.30 – 6.00 GiB 之间，均值 5.59。

这块卡有 7.99 GiB，桌面 baseline 占了约 1.2 GiB，也就是说
**Ollama 还留了大约 1.3 GiB 没动**。这是它自己的安全余量。

实测之前的估算器假设「显卡容量的 92% 可用」，即 7.36 GiB 的预算，比真实值
高了 34%。

---

## 5. 估算器错在哪，为什么

### 错误一 · 漏了一整项显存开销

把实测的 SIZE 对「有效 token 数」（`num_ctx × num_parallel`）做线性拟合，
得到每个 token **132 KiB**。但 KV Cache 本身只占 56 KiB：

```
KV 每 token = 2 × L × H_kv × d_head × b = 2 × 28 × 4 × 128 × 2 = 56 KiB
```

多出来的 76 KiB 当时被解释成**注意力矩阵缓冲区**。

因为设了 `OLLAMA_FLASH_ATTENTION=0`，推测 llama.cpp 无法把注意力计算融合
起来，必须把注意力分数完整算出来存在显存里，这块缓冲区的大小是：

```
注意力缓冲区每 token = n_batch × H × 4 = 512 × 28 × 4 = 56 KiB
```

对 Qwen2.5-7B 来说，这两项恰好相等，看起来解释得非常漂亮。

补上这一项之后，SIZE 的平均绝对误差从 1.5 GB 降到 0.24 GB。

> ⚠️ **这个解释后来被实验推翻了，见第 6 节。** 公式仍然拟合得很好，但它
> 描述的物理机理是错的。

### 错误二 · 显存预算是拍脑袋定的

`usable_fraction = 0.92` 完全是假设，没有依据。真实预算是第 4 节测出来的
5.5 GiB。现在它是一个有名字的常量，测量依据就写在旁边的注释里。

### 两处都修正之后

在 11 个配置上（剔除第 3 节那个存疑行）：

- SIZE 平均绝对误差：**0.24 GB**
- GPU 占比平均绝对误差：**1.0 个百分点**

## 6. 假设被证伪了

第 5 节把那多出来的 76 KiB/token 解释成「关掉 flash attention 导致的注意力
缓冲区」。这个解释可以被证伪，实验也做了。

### 实验设计

只改一个变量。`OLLAMA_FLASH_ATTENTION` 从 0 改成 1，重启服务和终端，
`check_env.py` 确认显示 `1 (期望 0)` 之后，用同一个 `payloads/ctx16384.json`
重测。其余条件（P=1、KV f16、同一模型、同一请求体）与之前完全一致。

### 结果

| | SIZE | PROCESSOR |
|---|---|---|
| FA = 0（原测量） | 6.5 GB | 12%/88% CPU/GPU |
| FA = 1（预测 5.56 GB） | **6.5 GB** | **12%/88% CPU/GPU** |

**完全没变，连百分比都一样。假设不成立。**

### 为什么实验什么也没测出来

最可能的原因：**Ollama 0.24 已经忽略 `OLLAMA_FLASH_ATTENTION` 这个变量**。
新版本把 flash attention 设为默认开启，该变量成了历史遗留。开和关给出逐位
相同的结果，正是一个不生效的开关该有的表现。

如果是这样，那么之前所有测量本来就是在 flash attention 开启下做的，
「关掉它才产生的缓冲区」在任何一次测量里都不曾存在过。

### 那 76 KiB/token 到底是什么

**目前不知道。** 这是个诚实的空白，不是遗漏。

已知的约束条件：

- 它随 `num_ctx × num_parallel` 线性增长（第 3 节的交叉验证保证了这点）
- 它似乎和注意力头数 \(H\) 相关，而不是 KV 头数 \(H_{kv}\)。证据是 14B：
  14B 的 \(H/H_{kv}\) 比例和 7B 完全不同，用「KV 的固定倍数」去拟合误差是
  0.85 GiB，用「\(n_{batch} \times H \times 4\)」这个形式误差是 0.14 GiB
- 但这只是一个数据点，属于弱证据

候选解释与能区分它们的实验：

| 候选 | 如何验证 |
|---|---|
| Ollama 的显存预估本身带固定裕度 | 对比 `/api/ps` 的 `size` 与 `nvidia-smi` 实际占用之差 |
| 与 `n_batch` 有关的某个缓冲区 | 改 `num_batch` 到 128 或 1024，看斜率是否随之变化 |
| KV Cache 实际不是 f16 存储 | 设 `OLLAMA_KV_CACHE_TYPE=q8_0`，看斜率是否减半 |
| 与模型架构相关的固定开销 | 换 llama3.1:8b（\(H/H_{kv}=4\)）测同样四个 ctx |

**其中第二个实验最便宜也最有区分度**：`n_batch` 只出现在这一项里，KV Cache
公式里没有它。如果把 batch 减半，斜率也跟着减半，就说明这一项确实和 batch
相关；如果斜率不动，这个形式就该整个换掉。

### 估算器怎么处理

那一项保留了，但改名为 `extra_context_gb`，并在代码注释里明确标注**机理未知**。
它是一个拟合得很好的经验项（11 个配置误差 0.24 GiB），不是一个有解释的物理项。
把它当成物理项写进 README 就是不诚实。

> 这一节记录的是一次失败的假设。保留它比删掉它有价值：一个能被自己的实验
> 推翻的假设，说明这个假设当初是被认真提出来的。

## 7. Day 6 矩阵的决策

- **上下文轴留在 7B-q4_K_M 上。** 拐点在 16384，远在这个模型原生上限 32768
  之内，所以拐点两侧各有足够的数据点，曲线画得出来。不需要换到 q8_0。
- **加一行 ctx 4096。** 那是 Ollama 的默认值，也就是大多数读者实际会遇到的
  配置。
- **并发轴从「可选」提升为「必做」。** 两组精确相符的交叉验证值得单独报告，
  不该只当脚注。
- **有余力再加一对 flash attention 对比**（ctx 16384，开 vs 关）。

## 8. 环境注意事项

- 桌面显存 baseline 在五次读数中波动了 0.6 GiB，取决于当时开了什么程序。
  Day 6 的所有测量必须在同一次会话里、关掉浏览器完成，并且每一行都记录
  `baseline_gb`。
- **SIZE 可复现，GPU 占比不可复现。** ctx 16384 测了两次：

  | | SIZE | PROCESSOR | baseline |
  |---|---|---|---|
  | 第一次 | 6.5 GB | 15%/85% | ~1.2 GiB |
  | 第二次 | 6.5 GB | 12%/88% | 1.65 GiB |

  SIZE 完全相同，说明它只由配置决定。层的切分则随当时的可用显存变化——
  Ollama 是在加载那一刻动态决策的。**因此报告 `gpu_ratio` 时必须同时报告
  baseline，单独的百分比没有意义。**
- `ollama ps` 的 SIZE 只保留两位有效数字。Day 6 应该改读 `/api/ps` 拿精确
  字节数。
- Ollama 的默认上下文是 4096，不是 2048。任何预测与实测的对比都必须用同一个
  值。
